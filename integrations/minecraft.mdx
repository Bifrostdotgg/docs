The Minecraft integration connects your Discord server to one or more Minecraft Java Edition servers. It provides account linking (tying a Discord user to their Minecraft username), whitelist management that syncs with Discord roles, RCON access for remote commands, a live server status display, and a native punishment engine for bans, mutes, warns and kicks.

## Account linking

A link ties one Minecraft name to one Discord account. Members start one from Discord and prove it is theirs with a 6-digit code shown in game.

### The account-linking panel

The panel is a Discord message with **Link Account**, **Unlink Account** and **My Account** buttons. Post it in any of these ways:

- The last step of Minecraft setup offers to post it.
- <DashboardLink to="settings/messages">**Settings \> Messages**</DashboardLink>, on the **Account linking panel**: **Post** sends it to a channel you pick. Posting into the channel it is already in updates that message; posting somewhere else adds a copy there and leaves the others where they are (see [Panels posted in more than one channel](/dashboard#panels-posted-in-more-than-one-channel)). You can also rewrite the panel's text there and keep its buttons.
- `/minecraft-setup panel` from Discord.

Members can also start from a slash command:

```text
/link-minecraft
```

### Getting the code

After a member enters their Minecraft name, the code reaches them in game:

- **A server that requires a whitelist** refuses their join and shows the code on the disconnect screen.
- **A network set to let anyone join** (see below) lets them in. With Heimdall plugin 3.0.0-rc.19 or newer, the code is shown as soon as they join, and straight away if they are already online. On Paper 1.21.7 or newer, with a 1.21.6 or newer client, it opens as a dialog with a **Copy code** button; everywhere else, including Bedrock players, it is a chat message you can click to copy. The prompt names the Discord account that asked, and warns the player never to give the code to anyone.
- **Any server** also gives the code on request: the player runs **/linkdiscord** in game.

The member then presses **Confirm Code** on their account panel in Discord and enters it.

Players can start in game too: **/linkdiscord** gives them a code without having started from Discord.

<Note>
On a network that lets anyone join, **/linkdiscord** needs plugin 3.0.0-rc.13 or newer. Older builds treat it as the whitelist module's command and only echo it back. Update the plugin with **/hd update** in game or from its download page.
</Note>

### Letting anyone join

Each network's policy, on its page under <DashboardLink to="minecraft/networks">**Minecraft \> Networks**</DashboardLink>, has **Anyone can join, linking is optional**. With it on, nobody is turned away, the whitelist is switched off on that network's servers, and players who want their Discord roles in game link as above. The rest of the network policy takes effect again when you turn it off.

Once linked, Heimdall can:

- Whitelist the member, automatically or after staff approval, depending on the network's policy
- Remove them from the whitelist if they lose access
- Sync their Discord roles to groups in game (<DashboardLink to="minecraft/settings">**Minecraft \> Settings \> Role sync**</DashboardLink>)
- Display their Minecraft username alongside their Discord profile in the customer portal

### Linked role

Heimdall can give every member who has linked a Minecraft account a Discord role, for example to open a channel only for players. Turn it on in **Minecraft \> Settings**, under **Who can link, and how**, and pick the role.

- The role is given as soon as the link is confirmed, whether or not the player is whitelisted yet. It works the same with the whitelist on or with linking only.
- It comes off when the member unlinks their last Minecraft account, or when staff delete the player for good.
- **Take it away from blocked players** (on by default) also removes the role while a player is blocked, revoked or removed by staff, and gives it back when they are unblocked.
- Members who linked before you turned it on get the role when you save. Changing the role moves everyone from the old role to the new one.
- Heimdall only takes the role back from members it gave it to, so anyone you gave it to by hand keeps it.

The bot needs the **Manage Roles** permission and a role above the linked role. A role with moderation or admin permissions, in Discord or in Heimdall, is refused, and so is a role that a Minecraft to Discord role sync mapping already gives.

## Whitelist management

Navigate to <DashboardLink to="minecraft/players">**Minecraft \> Players**</DashboardLink> in the dashboard to view the full whitelist status - who is linked, who is pending verification, and who has been manually approved or denied.

### Automatic whitelisting and approval

Each network's policy, under **Minecraft \> Networks**, decides what a link grants: **Auto-whitelist** whitelists a linked member on that network without review, and **Require staff approval** holds requests in a queue on the **Players** page for a decision. The whitelist is pushed to your servers by the Heimdall plugin, not through RCON.

How members link, how many accounts each may hold, and how long a code stays valid are under **Minecraft \> Settings \> Who can link, and how**.

```text
/import-whitelist
```

Imports an existing whitelist file from your Minecraft server, linking each username to their Discord account where a match can be found.

## Server status

```text
/mcstatus [server]
/minecraft-status
```

Displays the live status of your configured Minecraft server - online/offline, current player count, player list, and server version. The information is fetched directly from the Minecraft server protocol and does not require RCON.

The dashboard **Minecraft \> Networks** page shows the same information in a continuously updating format, per server.

## Player list

```text
/playerlist [public]
```

`/playerlist` is opt-in and off by default: it registers no command, and costs no command slot, until an admin turns on **Player list command** in **Minecraft \> Settings**. The command itself has no server option. The dashboard fixes what it lists when you turn it on: one claimed server, or, for a guild running more than one network, a whole network, grouped by which server each player is on. Members never pick a target themselves; they only see the one the dashboard was set to.

The reply is visible only to whoever ran the command, unless they add `public:true`, which posts the list in the channel instead. It is a one-shot reply and never updates itself. For a live card that keeps refreshing, use `/mcstatus watch` instead.

### Vanished players

Connected servers running Minecraft plugin `3.0.0-rc.13` or newer report which of their online players are vanished, recognising the `vanished` metadata key set by EssentialsX, SuperVanish, PremiumVanish, CMI and VanishNoPacket. Heimdall hides a vanished player's name from anyone who does not hold `minecraft.server.view_vanished`, everywhere a name is shown: `/playerlist`, `/mcstatus get`, and the dashboard's Online Players panel.

Player counts on the dashboard, the Players tile, its sparkline, and the overview, always show the visible count, for everyone, so they stay in step with the live updates. Someone who holds `minecraft.server.view_vanished` additionally sees a "+N vanished" chip beside the Players tile, and a Vanished badge on those rows in the Online Players panel. `/mcstatus get` works differently: a holder still gets the full list there, with `(vanished)` marks, and a count that includes them.

Public surfaces always hide vanished players, no matter who is looking: a watched status card, `/mcstatus send`, and `/playerlist public:true` never show them, even to the person who ran the command. Someone who does hold the permission still sees them in their own private reply, each one marked `(vanished)` so it is clear who their colleagues in the channel cannot see.

A backend running an older plugin build, or no plugin at all, cannot report vanish state, so its vanished players are listed like anyone else. On a network, if a holder runs `/playerlist` and at least one backend cannot report vanish, a one-line footnote warns that someone hidden may still be listed. There is nothing to configure for this: it is a limit of what that server can tell Heimdall, not a setting.

## Chat bridge

The chat bridge relays in-game chat into Discord channels, and Discord messages back into the game. Set it up on <DashboardLink to="minecraft/bridge">**Minecraft \> Chat Bridge**</DashboardLink> by adding a mapping: pick a Discord channel, which servers it talks to (one server, a network, or all servers), and which way messages travel. Each mapping also chooses whether chat, joins, leaves and deaths are relayed.

Nothing is stored. Messages are relayed and then discarded, on both the bot and the Minecraft server.

### ChatControl channels

If your servers run ChatControl with channels turned on, each mapping has a **ChatControl channels** section listing the channels your servers report. Only chat said in the channels you tick is relayed to that Discord channel, so staff and admin channels stay out of Discord unless you pick them.

- **Picking a channel is required.** ChatControl has no default channel, so a mapping with no channels picked relays no chat from a server where ChatControl channels are on. The mapping shows a warning until you pick one.
- **One Discord channel per audience.** To relay a staff channel, add a separate mapping for a staff-only Discord channel and pick only the staff channel there.
- **Discord to Minecraft goes into the first picked channel.** Messages sent in the Discord channel are shown only to players in that ChatControl channel, so replies in a staff Discord channel stay in the staff channel in game.
- **Servers without channels are unaffected.** A server without ChatControl, or with its channels turned off, relays chat exactly as before, to mappings with no channels picked.

<Note>
Channel filtering needs a Heimdall plugin build with ChatControl support on each server. An older build cannot tell channels apart and relays every channel, and Discord messages for a channel mapping are not sent to it at all. A proxy cannot tell channels apart either, so while any server reports ChatControl channels, chat relayed by a proxy is dropped. Let your backend servers relay their own chat.
</Note>

## RCON

RCON lets you run commands on the Minecraft server directly from Discord. Configure the connection in **Minecraft \> Settings \> RCON** with your server's RCON host, port, and password. RCON access is limited to members with the appropriate Heimdall permission.

## Minecraft server setup

Servers are added under **Minecraft \> Networks**: add a server, install the Heimdall plugin on it, and claim it with the code the dashboard gives you. The setup walks through each step and ends by offering to post the account-linking panel.

Guild-wide settings are under **Minecraft \> Settings**:

| Card | What it holds |
| --- | --- |
| **Server address** | The address shown to members when they are told to join |
| **Who can link, and how** | Whether a link is required to join, self-unlinking, accounts per member, code lifetime, reminders |
| **Role sync** | Discord roles mapped to groups in game |
| **RCON** | Host, port and password for running commands |
| **Player list command** | Which server or network `/playerlist` shows |
| **Messages** | What players see in game, and a link to edit the account-linking panel |

## Rules

**Minecraft \> Rules** is where you define what counts as an offense on your Minecraft server and how repeat offenses escalate. Each rule is an offense type - griefing, chat spam, and so on - with a tier ladder: the first breach might warn, a later one might kick, and a further one might hand off to your ban plugin or to native punishments, depending on your punishment mode under Enforcement.

Staff log a breach in game with the offend command, choosing the offense type; Heimdall looks up which tier the player is on and runs the command configured for that tier.

## History

**Minecraft \> History** is one timeline of everything that has happened to a player. The offense log that Rules feeds and the native ban, mute, warn and kick log are merged into a single list ordered by time.

They used to be two places, and the punishment list was a card at the bottom of the settings page, which is not where anyone looks for a ban.

The table shows Kind, Player, Reason, Staff, Length and Status. A punishment that can end on its own is badged **Temporary**; one that cannot reads **Permanent**.

### Filters

Four filters, all of them kept in the URL, so a filtered view can be pasted into a ticket and opened by somebody else.

| Filter | Accepts |
| --- | --- |
| **Kind** | All, Offense, Ban, IP ban, Mute, Warn, Kick, Other |
| **Status** | All, Active, Expired or done, Revoked or pardoned |
| **Player** | A name or a UUID |
| **Staff** | A staff name or a Discord ID |

Kind spans both ledgers: an offense whose tier warned the player is a **Warn** here, not only an **Offense**. **Other** covers the types nobody browses for by name (geo, subnet and freeze). Under Status, **Expired or done** groups a punishment that ran out with one that was over the moment it landed, such as a kick; they are labelled Expired and Done in the table, because only one of them ever had an end date.

The list pages with a **Load more** button that appends rows rather than replacing them.

### Acting on a row

**Revoke** lifts a punishment and **Pardon** lifts an infraction. Both ask for an optional reason and store it, which is the only record of why something was lifted. Revoking needs `minecraft.punishments.revoke`; pardoning needs `minecraft.offenses.pardon_infractions`.

### Issue punishment

The **Issue punishment** button in the page header opens a modal:

| Field | Notes |
| --- | --- |
| **Type** | Ban, Mute, Warn or Kick |
| **Player** | A name or a UUID |
| **Length** | Only for Ban and Mute. Blank means permanent |
| **Reason** | Free text |
| **Announcement** | Shown only if you hold `minecraft.punishments.silent` |

<Note>
History opens for anyone holding any of the offense view keys or any of the punishment keys, but the feed re-checks both families against you and returns only the halves you hold. Someone with `minecraft.offenses.view_infractions` and no punishment key opens History and sees no bans in it.
</Note>

## Enforcement

**Minecraft \> Enforcement** is how Heimdall punishes and what the public sees. It is Heimdall's native ban, IP-ban, mute, warn and kick engine for connected Minecraft servers. It replaces dispatching a console command to a separate banning plugin with Heimdall enforcing directly, and it keeps a single punishment record that History, `/mc-punish`, and the in-game commands below all read and write.

Every server has one of three modes, chosen from three cards on **Minecraft \> Enforcement** - and, for a network that has never had a mode chosen, as a step in the setup wizard:

| Mode | What happens |
| --- | --- |
| **Offenses only** | The default. Heimdall records offenses and runs the commands on your escalation tiers; your existing ban plugin, if you run one, stays in charge in game and nothing is enforced natively. Pick this if you do not want Heimdall enforcing punishments at all. |
| **Alongside your ban plugin** | Heimdall issues punishments through your existing plugin and mirrors them here, so the dashboard, appeals and the public bans page see everything. Your plugin stays the source of truth in game. Requires LiteBans on the server. Pick this as the first step of a cutover, so staff can see history before anything changes on the server. |
| **Heimdall runs bans** | No other ban plugin. Heimdall enforces bans, mutes, warns and kicks itself, with your screens, the public bans page and appeals all from here. Adds `/mc-punish` in Discord, and the in-game punishment commands below. Pick this once you have imported history and are ready to remove the old banning plugin. |

Switching modes takes effect immediately, so the dashboard asks you to confirm first and spells out what changes - which commands appear or disappear, and who enforces punishments afterward. Every punishment already recorded is kept no matter which mode you switch to or from.

### What is on the Enforcement page

- **Mode** - the Offenses only / Alongside your ban plugin / Heimdall runs bans switch above.
- **Enforcement settings** - root command aliases (one guild-wide toggle, no per-server override), silent-by-default, and the blocked-command list a mute enforces. All guild-level, all saved here, all gated by `minecraft.punishments.manage`.
- **Screens** - the nine MiniMessage segments a punished player reads, plus the two announcement templates. See [Screens](#screens) below.
- **Minecraft appeal form** - pick a Minecraft-specific appeal form to fill in `{appeal_url}` on the screens. Use a form separate from the Discord infraction appeal form.
- **Import existing punishments** - **Run import** asks the connected server to run its LiteBans, AdvancedBan, BanManager and vanilla `banned-players.json` importers in a single pass, skipping whichever it does not find. **Preview import** does the same reading and writes nothing, so you can see what a run would do first. IP addresses are hashed on that server before anything reaches Heimdall. Importing never pushes an enforcement update by itself, so it does not kick a player who happens to be online and never overrides a punishment that is already active for the same target, but a row imported still active is enforced by the normal sync afterward. The card for each run shows what came in, what is still in force, and anything lifted to match LiteBans.
- **Public bans page** - now under <DashboardLink to="cases/bans-page">**Cases \> Bans page**</DashboardLink>; this card links there. See below.

The punishment browser and the issue form are no longer here. They moved to [History](#history), which merges them with the offense log. An old `/minecraft/punishments` link still works: it lands on Enforcement, unless it carries one of the old browser's filters, in which case it lands on History with those filters translated.

### Cutover from LiteBans

If you are running LiteBans today, move over in this order. Every server needs Heimdall plugin 3.0.0-rc.22 or newer for the preview and for warns to be shown once.

1. **Alongside your ban plugin.** Switch to **Alongside your ban plugin**. Staff see history in the dashboard while LiteBans keeps enforcing, and every ban, mute or lift LiteBans makes from now on is copied to Heimdall.
2. **Permissions.** Grant the `heimdall.punishments.*` nodes to your staff ranks (see [In-game commands](#in-game-commands)), and `heimdall.admin` to whoever runs the import.
3. **Back up** the LiteBans database. It is also your way back.
4. **Preview the import.** Press **Preview import** on the Enforcement page, or run `hd import --dry-run` in the server console (or `/hd import --dry-run` in game). The preview reads everything a real import would and writes nothing. It reports:
   - how many bans, IP bans and mutes would still be in force;
   - how many rows match something Heimdall already copied while running alongside LiteBans;
   - how many Heimdall still enforces although LiteBans has lifted them. The import lifts those to match.
   - how many Heimdall holds that LiteBans does not, such as ones issued from Discord. Check these before you switch, because Heimdall enforces them too once it runs bans.
5. **Run the import.** Use **Run import**, or run `hd import` in the server console (`hdp import` on the proxy). Run it on each server that has its own LiteBans database. A failed batch is named in the result, and running it again carries on from there.
6. **Preview again.** It should find nothing new to import and nothing to lift. If it does, run the import again before you go further.
7. **Switch to Heimdall runs bans** during a quiet moment, with staff told to hold off on punishment commands.
8. **Stop each server and take `LiteBans.jar` out.** Keep the jar and its database until you are sure, since putting it back and switching to **Alongside your ban plugin** is the rollback.
9. Optionally turn on **Register root command aliases**, so the network's own `ban`, `mute` and similar commands register as Heimdall's own commands, rather than only the `hd`-prefixed ones. This is one guild-wide setting - there is no separate per-server toggle - and the aliases are only registered in **Heimdall runs bans** mode.

Imported warnings are history only. LiteBans already showed them to the player, so Heimdall does not show them again. A warning issued in Heimdall is shown to the player once: straight away if they are online, otherwise when they next join. The proxy shows it, or the server itself if it has no proxy in front of it.

Servers that never want the native engine can stay on Offenses only indefinitely; that is a supported end state, not a step on the way to Heimdall runs bans.

### In-game commands

<Note>
The commands in this section are Minecraft in-game and console commands, run on the connected server, not Discord slash commands. They are not covered by Heimdall's Discord [command reference](/docs/reference/commands).
</Note>

Once punishments mode is Alongside your ban plugin or Heimdall runs bans, the plugin registers an `hd`-prefixed family on backend servers and an `hdp`-prefixed family on the proxy:

```text
/hd ban       /hd tempban    /hd ipban
/hd mute      /hd tempmute   /hd kick      /hd warn
/hd unban     /hd unmute     /hd unwarn
/hd history   /hd banlist
```

Most punishment verbs take the same shape:

```text
/hd ban <player> [duration] [reason] [-s|-p]
```

A kick and a warn have no length, so theirs is `<player> [reason]` and nothing else, while `tempban` and `tempmute` require a length. Get a shape wrong and the verb tells you its own, whether you typed the `hd` spelling or a root alias.

**The duration can go anywhere after the player, and so can the flags.** The first whole token that is a duration becomes the length, and everything else in any order is the reason, so these are the same ban:

```text
/hd ban Steve griefing spawn 7d
/hd ban Steve 7d griefing spawn
```

A word with a duration buried in it stays a word: `abc5m` and `1day-old` are reason text, not lengths.

In **Heimdall runs bans** mode, the **Register root command aliases** toggle additionally registers the bare command names (`ban`, `mute`, `kick`, and so on) as in-game aliases. That is one guild-wide setting applying to every connected server, with no per-server override, and both spellings behave identically. Leave it off while a banning plugin like LiteBans is still installed, since both plugins would otherwise fight over the same command name; turn it on only after that plugin is removed. These in-game aliases are separate from, and share no code with, Heimdall's own Discord `/ban`, `/mute` and `/kick` moderation commands.

### Tab completion

Tab completion follows the same rule the parser does, so it never suggests a name into the middle of a reason. Flags are not counted when working out which word is the target, so a name still completes after a `-s`.

| Where you press tab | What is offered |
| --- | --- |
| The target position | Player names. Everyone online first, then everyone this server has seen or punished |
| The target of a revoke verb | Only players who actually have one of those to lift |
| A word starting with `-` | The `-s` and `-p` flags, and only if you may use them |
| After the target, on a verb that has a length, before one is typed | A short list of common lengths: 30m, 1h, 6h, 1d, 7d, 30d, perm |
| Inside the reason | Nothing |

Suggestions are capped at 100. An enforcer backend has no address history of its own, so it completes from online players and the punishment store only.

### Durations

One grammar, shared by the in-game commands, `/mc-punish`, and the dashboard's Issue punishment form, and pinned by a fixture table both the bot and the plugin test against. Lengths are kept in seconds, so `30s` is thirty seconds rather than rounding up to a minute.

| Unit | Spellings |
| --- | --- |
| seconds | `s`, `sec`, `secs`, `second`, `seconds` |
| minutes | `m`, `min`, `mins`, `minute`, `minutes` |
| hours | `h`, `hr`, `hrs`, `hour`, `hours` |
| days | `d`, `day`, `days` |
| weeks | `w`, `week`, `weeks` |
| months | `mo`, `month`, `months` (30 days) |
| years | `y`, `year`, `years` (365 days) |
| permanent | `perm`, `permanent` |

A month is always 30 days and a year always 365, on purpose: a ban has to be the same length whichever calendar month it was issued in.

- **Case-insensitive.** `1D12H` is `1d12h`.
- **Compound, with no spaces inside a token.** `1d12h`, `2h30m`, `1w2d3h`. Parts are summed, so `1h1h` is two hours. `2 hours` is two words and neither one is a length.
- **Whole tokens only.** A token is a length or it is not; there is no substring match. This is what lets the in-game parser pick the length out of a free-form command line without eating part of the reason.
- **Zero is not a length.** `0s` is not a duration, so a stray `0` in a reason cannot quietly issue a zero-second ban.
- **Ten years is the longest punishment anyone can issue.** Every surface a human types a length into agrees on that, so a typo'd `1000d` is refused wherever it was typed. Use permanent instead. Imports and offense tiers are not typed in and are bounded separately, and in **Alongside your ban plugin** mode a LiteBans ban longer than ten years is mirrored as permanent rather than refused, because the ban is already live over there and nobody is present to be told.

**A warn and a kick have no length.** Only a ban, an IP ban and a mute can be temporary; everything else is a moment rather than a state. A warning is a note on a record that does not expire, and a kick has already happened by the time it is recorded.

In game, those two verbs complete no lengths, and a command that carries one anyway is refused with a message naming the word, rather than having it quietly taken out of the reason. Put the word in the reason or drop it. This catches `perm` too, which is a length token even though it resolves to no length.

Permanent is spelled the same way everywhere: `perm` or `permanent`, or no length at all. In game that means omitting the token, in the dashboard's Issue punishment form it means leaving **Length** blank, and on `/mc-punish` it means omitting the `duration` option. All three accept the word and the blank interchangeably.

### Silent punishments

Every guild has a **Silent by default** toggle on the Enforcement page. A public punishment is announced in chat to everyone on the server; a silent one is announced only to staff holding the in-game permission node `heimdall.punishments.notify`, prefixed `(silent)` so it is obvious which is which.

Staff can depart from the guild default on a single punishment:

- **In game**, adding `-s` (silent) or `-p` (public) to a punishment command needs the in-game node `heimdall.punishments.silent`.
- **In Discord or the dashboard**, doing the same needs the dashboard permission key `minecraft.punishments.silent` ("Override silent punishments").

Either way, without the permission the flag is refused outright rather than silently dropped - a moderator never believes a punishment went out quietly when it did not. A flag that agrees with the guild default is always allowed, since it changes nothing.

On a proxied network, only the proxy announces punishments in chat - an enforcer backend never does - so it is the proxy's own permission nodes that decide who sees a silent announcement there. An expired punishment is never announced, and neither is one that a newer punishment has replaced.

On Bukkit, `heimdall.punishments.notify` and `heimdall.punishments.silent` are declared as op-default children of `heimdall.admin`, so an admin already holds both. Velocity and BungeeCord have no such descriptor to read, so grant both nodes to your staff ranks through your permission plugin (LuckPerms or similar) before you rely on them there.

In-game permission nodes are `heimdall.punishments.<action>`, one per action: ban, ipban, mute, warn, kick, unban, unmute, history, and dupeip. These do not inherit from `litebans.*` or any other plugin's nodes, so grant them to your staff ranks before you remove the old plugin, not after, or staff lose access the moment it comes out.

### Muted players

A mute is enforced by the backend a player is on. What the muted player sees:

- **The mute screen once.** They see the full mute screen when the mute lands while they are online, or at their first message if they were muted while away. It shows once per mute, on each server, each session.
- **A reminder after that.** Every message after the first gets one line, by default "You are muted for another 9m 59s." It is the **Mute reminder** segment under [Screens](#screens).

**Blocked commands.** The Enforcement page lists the commands a muted player cannot run (`/msg`, `/tell`, `/me`, `/r`, `/whisper` and `/w` by default). {/* docs-manifest-ignore -- Minecraft commands, not Heimdall's */}

- An entry blocks that command and anything typed after it, a whole word at a time. `ch send` blocks `/ch send hi` but not `/ch join`, and `me` blocks `/me waves` but not `/menu`. {/* docs-manifest-ignore -- Minecraft commands, not Heimdall's */}
- An entry also blocks a plugin's namespaced form of the command, so `me` blocks `/minecraft:me` too.
- A trailing `*` is ignored, so `tpa*` means `tpa`: it blocks `/tpa` but not `/tpaccept`.

Matching subcommands needs plugin 3.0.0-rc.24 or later. Before that, only the command's first word was matched, so an entry like `ch send` blocked nothing.

**Staff alerts.** Staff can be told when a muted player tries to talk. The alert reads `[Heimdall] Steve tried to speak while muted`, or `tried to use a blocked command while muted`. Two in-game permission nodes control it:

| Node | What it adds |
| --- | --- |
| `heimdall.punishments.notify.muted` | The alert itself |
| `heimdall.punishments.notify.muted.content` | A second line with what the player tried to say, or the command as typed |

Both are opt-in. Nobody holds them by default, not even operators, and `heimdall.admin` does not include them. Grant them to the staff ranks that should see alerts.

- **Where alerts appear:** only on the server that refused the message, so on a network with several backends, staff on one backend do not see attempts on another.
- **Throttling:** each mute raises at most one alert every 30 seconds while the player stays online. The next alert says how many attempts it covers, for example `(4 more since)`. Rejoining, or a new mute, starts a fresh count.
- **Hidden mutes:** an alert for a hidden mute also needs `heimdall.punishments.hidden`, and is prefixed `(hidden)`.
- **Privacy:** what the player said is shown as plain text, so it cannot put formatting or links into staff chat. It is never stored, and never sent to Heimdall or to Discord.

Staff alerts and the editable reminder need plugin 3.0.0-rc.25 or later.

### Screens

Screens are what a punished player reads. They are [MiniMessage](https://docs.advntr.dev/minimessage/format.html) templates edited on the Enforcement page, not in any file on the server, and they ship with a Bifrost-branded default rather than a blank box.

There are ten segments:

| Segment | Where it is shown |
| --- | --- |
| **Base** | A header block included at the start of the ban, mute, kick and warn screens and their permanent variants. Not used by the mute reminder or the announcements |
| **Ban screen** | On the disconnect screen when a banned player tries to join |
| **Ban, permanent variant** | Optional. Replaces the ban screen when the ban never expires |
| **Mute screen** | In chat, once per mute: when it lands while the player is online, or at their first message |
| **Mute, permanent variant** | Optional. Replaces the mute screen when the mute never expires |
| **Mute reminder** | In chat, for every message a muted player tries to send after the first. Left empty, the default is used |
| **Kick screen** | In chat when a player is kicked |
| **Warn screen** | In chat when a player is warned |
| **Issue announcement** | The chat line posted when a punishment is issued |
| **Revoke announcement** | The chat line posted when a punishment is lifted early |

Each segment is capped at 4000 characters.

#### Tokens

Values are escaped before the template is parsed, so a reason cannot inject formatting.

| Token | Is | Valid in |
| --- | --- | --- |
| `{base}` | The rendered base segment | The six screens, not the base itself, the mute reminder or the announcements |
| `{server}` | Your Discord server's name | Every segment |
| `{player}` | The punished player's username | Every segment |
| `{staff}` | Who issued it (Console when unattributed) | Every segment |
| `{id}` | The punishment id, for appeals and lookups | Every segment |
| `{type}` | Temporary ban, Permanent ban, Temporary mute, Kick, Warning, and so on | Every segment |
| `{reason}` | The reason, empty when none was given | Every segment |
| `{duration}` | The original length (`1d`, `3d 4h`), empty when permanent | Every segment |
| `{remaining}` | Time left (`23h 42m`), empty when permanent | Every segment |
| `{date_start}` | When it was issued, `yyyy/MM/dd HH:mm` server time | Every segment |
| `{date_end}` | When it expires, empty when permanent | Every segment |
| `{appeal_url}` | The appeal form link, empty when no form is chosen | Every segment |
| `{verb}` | banned, temporarily banned, muted, unbanned, and so on | The two announcements only |

A token used where it means nothing is refused when you save, rather than accepted and rendered as nothing. `{base}` in an announcement and `{verb}` on a ban screen are both rejected with a message naming the tokens that are available there.

#### Optional segments

Text wrapped in `[ ... ]` is dropped whenever any token inside it resolves empty, and a line left blank by that is removed entirely. This is what keeps the defaults short: a permanent ban loses its Length line, a guild with no appeal form loses its Appeal line, and an announcement with no reason loses its "for" clause, without needing a separate template for every combination.

To print a literal bracket, escape it as `\[` or `\]`.

The ID line is wrapped this way too. A punishment issued while the bot was unreachable only has a local id that no appeal can be opened with, so the row disappears for the length of the outage and comes back with the real id once it syncs.

#### Permanent variants

The ban and mute screens each have an optional permanent variant, and both are blank by default. Blank means "reuse the temporary screen", which works because `{type}` already reads "Permanent ban" and the Length line drops itself.

Write one only if a permanent ban wants a different layout, not just different wording. A variant you write **replaces** the temporary screen completely, so start it with `{base}` if you want the header back.

#### Reset to default

Each segment has its own **Reset to default** button, and the permanent variants have **Clear** instead, since blank is their normal state.

Reset does not paste today's default text into your guild's settings; it clears the value, so the segment tracks the shipped default and picks up any future improvement to it. A segment you have written stays exactly as you wrote it.

#### Legacy colour codes are refused

Screens are MiniMessage. A section sign (`§`) is refused when you save, because the plugin hands the template to MiniMessage's parser, which does not know what a section sign is, and the player would get the codes printed at them as tag soup. Use tags instead: `<red>`, `<bold>`, `<gradient:#a:#b>`.

#### Customising the base header

The default base opens with your Discord server's name in the Bifrost gradient. To put your network's own wordmark there instead, edit just that first line and leave the rest:

```text
<b><red>Example Network</red></b> <gray>Moderation</gray>
<gradient:#c278b0:#a292dc><st>                                          </st></gradient>
[<gray>Staff</gray> <dark_gray>»</dark_gray> <yellow>{staff}</yellow>]
<gray>You</gray> <dark_gray>»</dark_gray> <yellow>{player}</yellow>
[<gray>ID</gray> <dark_gray>»</dark_gray> <yellow>{id}</yellow>]
```

Every screen that starts with `{base}` picks the change up, so this is the one place to edit for branding.

<Note>
Clients older than 1.16 cannot render a hex gradient. Adventure maps each colour to the nearest of the sixteen legacy colours, so the header becomes light purple and the dividers grey. Readable, less pretty, and nothing to configure.
</Note>

### Announcements

The two announcement templates are the chat lines your server sees when a punishment is issued or lifted. They use the same tokens and the same optional-segment rule as the screens, plus `{verb}`.

```text
Issue:  {staff} {verb} {player}[ for {reason}][ ({duration})]
Revoke: {staff} {verb} {player}[ for {reason}]
```

`{verb}` is chosen by the punishment type and by whether it has an expiry: "banned", "temporarily banned", "muted", "unbanned", and so on. Because the reason and duration clauses are optional segments, a permanent ban with no reason reads "Adam banned Steve" and nothing dangles.

Three things are not configurable here, on purpose:

- **The `(silent)` prefix.** A silent punishment produces the same sentence with `(silent)` in front, shown only to holders of `heimdall.punishments.notify`. It is prepended by the plugin and cannot be removed from a template, because a template that could drop it would be a way to announce a silent punishment loudly. Staff always learn that an action happened; what silence buys is that the server at large does not.
- **What an announcement never contains.** No address, no digest, no UUID. An IP ban announces as "IP-banned". The line is always a single line: a newline in a reason is folded to a space.
- **Which types announce at all.** Geo, subnet and freeze name no player, so they produce no line, and neither does a punishment whose target name is not known.

**Clearing a template turns that announcement off.** An empty box is the switch, and it turns the line off for everybody, staff included. That is deliberate: a guild that has said it wants no broadcast has said so about the broadcast, not about who reads it. Silencing the server at large while still telling staff is what `-s` is for, and that is a per-punishment decision. An empty template can only come from you clearing the box, because the bot sends its default whenever the value is unset and the plugin falls back to the same default whenever the bot sends nothing at all.

### `/mc-punish`

`/mc-punish` is Heimdall's Discord-side surface for punishments. It is only registered in servers where punishments mode is Alongside your ban plugin or Heimdall runs bans, so an Offenses only server pays no command slot for it. Its `ban`, `ipban`, `mute` and `warn` subcommands each take an optional silent flag, gated the same way as the in-game `-s`/`-p` flags described under Silent punishments above.

| Subcommand | Does | Permission key |
| --- | --- | --- |
| `/mc-punish ban` | Ban a player, with optional duration and silent flag | `minecraft.punishments.issue` |
| `/mc-punish ipban` | Ban a connecting IP, optionally attached to a player | `minecraft.punishments.issue` |
| `/mc-punish mute` | Mute a player, with optional duration | `minecraft.punishments.issue` |
| `/mc-punish warn` | Warn a player | `minecraft.punishments.issue` |
| `/mc-punish kick` | Kick a player | `minecraft.punishments.issue` |
| `/mc-punish unban` | Revoke an active ban or IP ban | `minecraft.punishments.revoke` |
| `/mc-punish unmute` | Revoke an active mute | `minecraft.punishments.revoke` |
| `/mc-punish history` | Show a player's punishment history | `minecraft.punishments.view` |

The `duration` option appears on `ban`, `ipban` and `mute` only, and takes the [grammar above](#durations). Omit it for a permanent punishment, or say `perm`; both mean the same thing here.

### Public bans page

The public bans page lives in [Cases](/moderation/cases#public-bans-page) now, at **Cases \> Bans page**, and can list Discord bans beside Minecraft ones. Your existing link and who could see what carried over unchanged when it moved. Who sees what is set in tiers (Public, Signed in, Members and role tiers), with Minecraft bans, IP bans and mutes, reasons, staff names and expired entries ticked per tier.

The page lives at `/<nanoId>` on your bans site host, a random id for the server rather than its Discord id. A visitor who needs to sign in does so with Discord through the main dashboard; the bans site itself never runs its own Discord sign-in. A punishment staff revoked early is never listed.

Each active Minecraft row carries its case number and an **Appeal** link that names that case, so the appeal lands on the right one.

The page never shows an IP address or a hashed digest, on the public view or the signed-in one.

### Player page and alt list

The Minecraft player page (**Minecraft \> Players**, then a player) shows a combined timeline of that player's punishments and offense-ladder infractions, with the length and a temporary or permanent badge on each punishment.

A "Shares an address with" card lists other accounts that connected from the same address as this player, without ever showing that address. It needs `minecraft.trace.view_trace`, not the punishments keys, because it exists to surface alt associations. It merges two sources: punishment records whose hashed address digest matches (labelled "From punishment records"), and a live query to the connected servers' own address history (labelled "Seen on your servers"). Only a gatekeeper proxy or a standalone server keeps that address history, so a backend server sitting behind a proxy cannot answer it, and the card names the gap rather than showing an empty list: it can say no proxy or standalone server could be asked, that no server which answered has ever seen this player, or, once both sources have genuinely come back empty, that no other account shares an address with this player. Each source is capped at 50 accounts, noted when a source is truncated. Names shown are whatever a server last saw for that account and can be stale, so every row links by the account's UUID, never by name.

<Note>
Heimdall never displays an IP address, on the player page, the bans page, or anywhere else in the dashboard. On its own database it stores an HMAC digest of each IP using a per-guild salt it holds, which is enough to match two connections to the same address but is not shown anywhere in the UI. That digest is not a cryptographic privacy boundary against someone with database and salt access, only against what the UI displays. A shared address is not proof of a shared owner.
</Note>

### If Heimdall is unreachable

Every connected server, proxy and backend alike, keeps its own local copy of active punishments and checks it directly, so a login or a chat message is never held up waiting on Heimdall. A banned player still cannot join and a muted player still cannot talk during an outage. A ban or mute issued while disconnected applies immediately to that server's own copy and queues to sync once the connection returns; other servers do not see it until then. A ban issued at the proxy still holds the whole network, since every login passes through the proxy, while a mute issued on one backend stays local to that backend until it reconnects.

The screens keep working too, from the last configuration the server received, so a player banned during an outage still reads your wording rather than a blank screen.
